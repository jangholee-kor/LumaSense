# 개발 기록

## 2026-11-02 · Phase 1 구현과 회사 초기 시험

Windows 11 Pro 빌드 26200, Python 3.12.2, PySide6 6.11.0에서 구현·시험했다.
프로젝트 구조와 밝기 백엔드는 `c506fac`, GUI·트레이와 전원 시험 기능은 `bdb7b63`으로 커밋하고 각 작업 직후 푸시했다.
재현 스크립트와 검증 기록을 마지막 작업 단위로 정리했다.

### 구현

- PySide6 GUI, 시스템 트레이, 중복 실행 방지와 JSON 설정 저장
- Twinkle Tray 경로·모니터 자동 탐색, 전체 ID 선택과 20/50/80% 수동 밝기 요청
- Windows 화면 절전, 5초 카운트다운과 취소
- SC_MONITORPOWER, SetThreadExecutionState, 선택적 SendInput 복귀
- 독립 프로세스의 예약 복귀와 추가 복귀 요청
- API 결과와 실제 화면 관찰을 분리한 시험 ID별 JSON Lines 로그
- 고정 의존성 설치, GUI 실행, 자동 테스트, 실제 장치 시험과 다음 단계 확인 스크립트

### 자동 검증

자동 테스트 24건이 통과했다.
CLI 오류·시간 초과, 모니터 목록 파싱, 대상 ID 검증, 밝기 복원, 설정 검증, 카운트다운 취소, 안전장치 준비 실패 시 절전 차단, 중복 명령 차단과 GUI 스레드 분리를 확인했다.
주 실행 프로세스를 즉시 종료해도 별도 프로세스가 모의 복귀 요청을 수행하는 통합 테스트도 통과했다.
GUI smoke 실행과 한글 렌더링을 확인했다.
GUI 작업 객체가 일찍 해제되어 완료 신호가 누락되던 오류를 수정하고 해당 동작을 테스트로 검증했다.
PowerShell 진단 출력의 한글 인코딩을 UTF-8로 지정했다.

### 실제 API 시험

사용자가 회사 주 모니터를 Q27U2G5R4-로 정정했다.
보조 모니터는 27B2H2이며 집의 모니터는 Philips 32M2N8900이다.
회사에서는 Q27U2G5R4-와 27B2H2 두 대가 검색됐다.
아래 시각은 한국 시간이며 원본 이벤트의 시각은 UTC이다.

| 시험 | 결과 | 물리 동작 판정 |
|---|---|---|
| 두 회사 모니터의 수동 슬라이더 밝기 제어 | 사용자 직접 확인 | 성공 보고, 구체적인 밝기 단계와 HDR/SDR 상태는 미기록 |
| 사용자 GUI 절전·복귀 정밀 재시험 | 5초 카운트다운, monitor_power 복귀 지연 5초, 마우스 이동 해제 | 화면이 꺼진 시점부터 Q27 12.3초, 27B2H2 14.88초에 켜짐 확인 |
| 27B2H2 밝기 20/50/80% | CLI OK, Twinkle Tray 보고값 20/50/80% 일치 | 관찰 대기 |
| 기존 밝기 복원 | 24% 요청 후 보고값 24% 확인 | 관찰 대기 |
| 12:03:02 전체 화면 절전 요청 | SC_MONITORPOWER(2) 접수 | 실제 꺼짐 관찰 대기 |
| 12:03:12 monitor_power 1차 복귀 | API 접수, 12:03:17 execution_state 추가 요청 | 개별 복귀 성공 관찰 대기 |
| 12:03:47 전체 화면 절전 요청 | SC_MONITORPOWER(2) 접수 | 실제 꺼짐 관찰 대기 |
| 12:03:57 execution_state 1차 복귀 | API 접수, 12:04:02 monitor_power 추가 요청 | 개별 복귀 성공 관찰 대기 |
| 마우스 이동 복귀 | 구현 및 모의 테스트 | 실제 장치 시험 미수행 |
| Philips 32M2N8900, HDR/SDR 비교 | 집에서 별도 시험 필요 | 미검증 |

밝기 시험 ID는 `8da1fd2e14664f63a2dc0c860e59c842`이다.
monitor_power 1차 복귀 시험 ID는 `35c86cc8923d46079d4bc889dd097843`, execution_state 1차 복귀 시험 ID는 `7936ccb1ea2142659d2826f84498946a`이다.
원본 실행 로그는 `%LOCALAPPDATA%\SmartMonitorController`에 있고 필요한 시험 이벤트를 [회사 시험 기록](validation/office-2026-11-02.json)에 보관했다.
API 접수와 Twinkle Tray 보고값만으로 실제 화면의 밝기·절전·복귀가 성공했다고 판정하지 않았다.
사용자가 두 모니터에서 슬라이더 밝기 제어가 정상 동작한다고 직접 보고한 결과는 [사용자 관찰 기록](validation/office-user-observations-2026-11-02.json)에 별도로 보관했다.
이 보고는 특정 밝기 세 단계나 기존 자동 복귀 시험의 관찰 결과로 확대하지 않았다.
이후 사용자가 첨부한 설정 화면과 함께 5초 뒤 절전, 꺼진 뒤 약 5초 자동 복귀를 확인했다.
해당 설정과 일치하는 완료 로그 시험 ID는 `0ba39fe1ed82432a80cad05ee057547d`이며 12:14:42 절전 요청, 12:14:47 monitor_power 1차 요청, 12:14:52 execution_state 추가 요청이 기록됐다.
이후 정밀 재시험에서 사용자가 화면이 꺼지자마자 측정을 시작해 Q27U2G5R4-는 12.3초, 27B2H2는 14.88초에 켜졌다고 보고했다.
이 실측값으로 앞선 약 5초 추정과 monitor_power의 잠정 성공 판정을 갱신했다.
첨부 화면의 절전 명령 수와 같은 설정이 일치하는 최신 완료 로그는 `28c937d2098341bab4930a44994c2f35`이며 한국 시간 12:16:40에 절전, 12:16:45에 monitor_power, 12:16:50에 execution_state 요청이 기록됐다.
두 화면 모두 자동 복귀한 결과는 성공으로 기록하되 두 API 요청이 모두 가시적인 복귀보다 먼저 실행되어 개별 API의 기여는 미확정으로 남겼다.
주 모니터보다 보조 모니터가 2.58초 늦게 켜졌으며 디스플레이의 실제 복귀 지연과 API별 효과를 이 시험만으로 구분하지 않았다.
마우스 이동 복귀는 해제된 설정이었고 입력 개입 여부와 HDR/SDR 상태는 별도로 기록되지 않았다.
회사 환경에서 마우스 이동 방식의 추가 시험은 현재 필수 항목으로 잡지 않았다.

### 단계 판정

Phase 1의 프로그램 구현과 자동 테스트를 마쳤으며 회사 두 모니터의 수동 밝기 제어는 사용자가 확인했다.
회사 환경에서 두 화면의 절전과 자동 복귀는 사용자가 정밀 재시험으로 확인했다.

Phase 2 펌웨어와 GPIO 배정, ESP-IDF 빌드·플래시는 수행하지 않았다.

## 2026-11-02 · 추가 복귀 간격 설정

기존 시험에서는 1차 요청 후 5초 만에 다른 API를 호출해 12.3초·14.88초의 화면 복귀 원인을 분리할 수 없었다.
GUI에 `추가 복귀 간격`을 추가하고 5~60초 범위에서 조절하도록 했다.
기본값은 30초이며 기존 설정의 모니터 선택과 1차 복귀 지연 등은 유지한다.
1차 복귀 5초와 추가 간격 30초를 설정하면 1차 요청은 약 5초, 추가 요청은 약 35초에 수행한다.
마우스 이동을 허용한 경우에도 추가 API마다 같은 간격을 기다린다.
GUI에 요청 예정 시점과 시험 ID를 표시하고 시험 버튼의 대기 시간을 전체 요청 일정에 맞췄다.
창 높이가 부족하면 내용을 스크롤하며 로그 폴더·숨기기·종료 버튼은 아래에 고정했다.

CLI에 `--fallback-seconds`를 추가하고 독립 복귀 프로세스에 같은 값을 전달한다.
API 호출 직전의 `wake_request_started` 이벤트를 추가했으며 설정값과 첫 추가 요청 예정 시점을 준비 로그에 남긴다.
이 변경 전 실행 로그는 종전의 추가 간격 5초에 해당하므로 새 기본값으로 재해석하지 않는다.

자동 테스트 37건이 통과했다.
추가 간격의 범위 검사, 기존 설정 호환, 실제 복귀 함수에 전달되는 대기 순서, UI의 예정 시점 표시·설정 잠금·시험 종료 시간과 독립 프로세스 전달을 검증했다.
독립 프로세스 통합 테스트는 모의 전원 API로 수행했고 실제 화면 절전은 요청하지 않았다.
수정한 UI를 렌더링해 새 옵션과 한글 표시를 확인했다.
추가 간격을 늘린 실제 모니터 시험은 사용자가 두 API를 하나씩 선택해 수행한 뒤 기록한다.

## 2026-11-02 · 추가 간격 30초의 첫 회사 시험

수정 버전 실행 후 사용자가 38초에 화면이 깨어났다고 보고했다.
시험 ID는 `ec56b936f272408cbcda38278d251b0a`이며 monitor_power 1차 지연 5초, 추가 간격 30초, 마우스 이동 해제 설정이 로그에 확인됐다.
한국 시간 12:30:00 절전 요청 후 12:30:05에 monitor_power, 12:30:35에 execution_state 요청을 시작했다.
두 API 모두 정상 반환했으며 38초의 가시적인 복귀는 execution_state 추가 요청 이후에 해당한다.
execution_state가 화면 복귀에 기여했을 가능성을 뒷받침하지만 monitor_power의 지연 효과를 이 한 번의 시험만으로 배제하지 않았다.
monitor_power의 개별 성공은 미확정으로 유지하며 다음 시험에서 execution_state를 1차 방식으로 선택한다.
이번 보고의 모니터별 복귀 시각과 입력 개입 여부는 기록되지 않았다.
해당 실행 이벤트는 [추가 간격 시험 로그](validation/office-delayed-fallback-2026-11-02.json)에 보관했다.

## 2026-11-02 · execution_state 1차 복귀 성공 확인

사용자가 SetThreadExecutionState를 1차 방식으로 선택하고 복귀 지연 5초, 추가 간격 30초, 마우스 이동 해제 설정으로 시험했다.
화면이 꺼진 시점부터 주 모니터 Q27U2G5R4-는 6.86초, 보조 모니터 27B2H2는 8.81초에 켜졌다고 보고했다.
시험 ID는 `bc4591b033c646d9befec1e84718ccad`이다.
한국 시간 12:56:42 절전 요청이 기록됐고 12:56:46에 execution_state 1차 요청, 12:57:16에 monitor_power 추가 요청을 시작했다.
두 화면 모두 추가 API를 호출하기 전에 켜져 이번 회사 환경의 SetThreadExecutionState 복귀를 실기 성공으로 기록했다.
5초로 설정한 값은 API 요청 지연이며 실제 화면이 켜질 때까지는 모니터와 연결 경로의 지연이 포함된다.
관찰과 실행 이벤트는 [execution_state 1차 시험 로그](validation/office-execution-state-2026-11-02.json)에 보관했다.
회사 환경에서는 execution_state를 우선 사용할 근거를 확보했으며 monitor_power 단독 성공 여부와 집 Philips 32M2N8900 검증은 미확정으로 유지한다.

## 2026-11-02 · 펌웨어 우선 구현

사용자 요청에 따라 실물 검증 대기를 후속 구현의 차단 조건에서 제외했고 상태 보고 명령은 기본 종료 코드 0을 반환하도록 변경했다.
실물 검증 미충족을 실패 코드로 처리하려면 `--require-physical`을 지정한다.
이어 사용자가 실제 펌웨어를 먼저 구현하는 순서와 실물 모듈 MCN16R8을 확인해 ESP32-S3 센서 펌웨어를 우선 구현했다.
실물 배선은 아직 확정되지 않아 GPIO8/9 I²C, GPIO16/17 UART를 변경 가능한 예시로 제공했다.

BH1750 연속 고해상도 측정, LD2412 기본·공학 모드 파싱, 오래된 데이터와 센서 오류 검출, USB JSON Lines 전송을 구현했다.
USB의 ping·상태 조회·전송 주기·레이더 공학 모드·거리문·민감도 명령은 실제 ACK를 확인하도록 구성했다.
센서 오류나 레이더 보정 상태를 인체 부재나 조도 0으로 바꾸지 않으며 unavailable 값은 null로 전송한다.
LD2412 V1.06에는 CRC 필드가 없으므로 길이·마커·상태 검사만 구현하고 CRC 검증을 했다고 표시하지 않는다.
USB 수신 버퍼·레이더 파서 길이와 명령 숫자 범위를 제한하고 GPIO 중복·예약 핀을 검사한다.

ESP-IDF 5.5.4에서 기본·octal PSRAM 프로필의 빌드와 크기 검사가 통과했다.
기본 앱은 264160바이트, PSRAM 앱은 271632바이트이며 각각 1MiB 앱 파티션에 들어간다.
기본 빌드에서 PSRAM을 사용하지 않고 별도 PSRAM 빌드는 octal 80MHz 초기화와 메모리 검사를 포함한다.
빌드 중 누락된 esp_driver_gpio 의존성을 수정한 뒤 두 프로필을 다시 빌드했다.
두 프로필의 통합 바이너리·개별 바이너리·SHA-256 manifest를 ZIP으로 만들고 해시·구성·ZIP 무결성을 검사했다.
[펌웨어 빌드 기록](validation/firmware-build-2026-11-02.json)에 결과를 보관한다.

같은 LD2412 C 파서를 PC GCC에서 실행해 제조사 예제·모든 프레임 분할 위치·노이즈·손상 프레임·ACK·보정 상태를 검증했다.
Windows 자동 테스트는 센서 프로토콜 검사 16건을 포함해 53건 통과했고 pip check, Python 컴파일과 기존 GUI smoke 실행도 통과했다.

사용자는 자리 비움 때 화면이 꺼지고 돌아오니 자동으로 켜졌다고 확인했다.<br>
해당 구간의 센서 450건은 모두 정상이었고 감지 251건·미감지 199건, 최대 수신 간격 0.234초와 순번 누락 0건을 기록했다.<br>
정상 복귀 후 독립 감시 프로세스의 lease_released 이벤트를 확인했다.

자동 절전이 활성화된 상태에서 사용자가 PC 쪽 USB 케이블을 빼고 5초 후 같은 포트에 다시 연결했다.<br>
앱은 시리얼 오류를 SENSOR_ERROR로 처리했고 USB 일련번호로 COM3를 다시 연결한 뒤 약 5초 안정화를 거쳐 인체 감지 상태로 돌아왔다.<br>
케이블 분리 이후 새 절전 요청은 없었고 사용자는 센서 재연결과 화면이 계속 켜져 있음을 확인했다.<br>
의도적인 전원 분리에 따른 MCU 재시작은 수신 안정성 오류와 구분했다.<br>
집 자동 제어 기록과 Phase별 상태에 결과를 반영했으며 30분 정지 착석·반복 이석·거리 경계와 24시간 실행은 통과로 표시하지 않았다.

## 2026-11-02 · 알림을 늦춘 SC_MONITORPOWER 단독 복귀 판정

자동 밝기·절전을 끈 상태에서 monitor_power 첫 요청을 10초, 추가 execution_state 요청을 70초로 분리해 재시험했다.<br>
시작 후 55초 동안 질문을 보내지 않고 기다린 뒤 사용자는 질문 전에는 화면이 꺼져 있었다고 확인했다.<br>
첫 API는 약 0.022초에 정상 반환했지만 절전 뒤 약 50초 관찰 구간에서 실제 화면이 켜지지 않아 monitor_power 단독 복귀를 실패로 기록했다.<br>
추가 API의 정상 반환은 앞선 단독 복귀 성공의 근거로 사용하지 않는다.<br>
자동 복귀 방식은 알림 전 실제 켜짐을 확인한 execution_state로 유지한다.

Phase 1 기록에 방식별 성공·실패를 반영하고 시험 가이드에는 질문·메시지·앱 알림과 실제 화면 켜짐을 구분하는 절차를 추가했다.<br>
첫 시험의 긴 API 지연은 이후 시험에서 재현되지 않았으며 당시 원인을 확정하지 않았다.

검증 후 수동·자동 복귀 방식을 execution_state로 저장하고 자동 밝기·절전을 껐으며 기존 밝기 56% 복원 보고값을 확인했다.<br>
센서 연결은 유지했고 30분 정지 착석 검증은 사용자 요청으로 보류했다.
